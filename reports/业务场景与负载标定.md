# 业务场景与负载标定

## 1. 为什么重新标定

旧版场景把标定得到的单 AC 饱和吞吐当作“全网容量”，再按业务比例分配 Mbps。这个做法没有把每个小包单独付出的 PHY 前导码、ACK、SIFS、AIFS、初始退避、碰撞和重传算进去。因而 `22.8/54=42.2%` 并不表示旧 S2 只有四成空口负载；对大量 160 B VO 包逐包计算后，旧 S2 即使不发生碰撞和重传，串行空口时间下界已经约为 1.293。旧 S4 的相同下界约为 1.425。这解释了为什么旧 S2/S4 会长期积压并饿死 BE/BK。

本阶段没有修改默认 EDCA，也没有按 DDQN 的结果挑场景。所有负载点都先用 Default EDCA、accounting schema 3 和固定独立 seed 扫描，再依据可服务性选取。

## 2. 固定不变的仿真条件

- ns-3.44，802.11a，20 MHz，数据 54 Mbit/s、控制 6 Mbit/s；
- 1 AP、10 STA，无 A-MPDU、无 Block ACK、无随机 PHY 错误；
- retry limit 为 7，MAC 队列寿命为 10 s；
- 队列上限仍为 VO/VI/BE/BK = 100/200/500/500 包；
- DATA、ACK、AIFS、退避、内部虚拟碰撞、重传、最终失败和队列过期均保留；
- 负载扫描采用 10 s 业务预热和 20 s 测量；比例先按每个 seed 计算，再跨 seed 求均值。

后端加入 S5 两状态到达率时，只改变下一次业务到达的间隔；EDCA 核心和已验证的统计回调没有改动。修改后重新构建 ns-3、重跑 Stage 0 和容量标定，Stage 0 通过，容量仍为 27.30225 Mbit/s。

## 3. 旧场景的实际含义

| 场景 | 每 STA 总负载 (Mbit/s) | 全网目标 (Mbit/s) | Payload/54M | 无碰撞空口时间下界 | 结论 |
|---|---:|---:|---:|---:|---|
| S1 | 1.502 | 15.016 | 0.278 | 0.597 | 轻载至可服务中载 |
| S2 | 2.280 | 22.800 | 0.422 | 1.293 | 持续过载，历史压力对照 |
| S3 | 2.321 | 23.207 | 0.430 | 0.862 | BE 主导但可服务 |
| S4 | 2.900 | 29.000 | 0.537 | 1.425 | 持续过载，历史压力对照 |

空口时间下界按每个未聚合包的一次 DATA + SIFS + ACK + AIFS + 平均初始退避计算，不含碰撞、重传和排队，因此只能作为“至少需要多少空口时间”的透明下界，不能替代 ns-3 实测。

粗扫覆盖旧业务组成的 0.40、0.55、0.70、0.85、1.00、1.15 倍，每点 2 个 seed，共 48 次。关键结果如下：

- 旧 S1×1.0 的总交付率为 99.995%，VO/VI p95 为 0.683/1.106 ms；默认 EDCA 已很好。
- 旧 S2×0.70 的总交付率已降到 85.64%，BE/BK 交付率仅 20.1%/8.0%；×1.0 时总交付率 73.08%，VI 成功包 p95 为 464 ms。
- 旧 S3×1.0 的总交付率约 99.998%，VO/VI/BE/BK p95 为 0.888/1.666/7.507/16.338 ms；拐点在 1.0 以上。
- 旧 S4×0.70 的总交付率为 84.74%，BE/BK 交付率为 45.8%/11.3%；×1.0 时 VI p95 为 219.6 ms，BE/BK 几乎没有服务。

这些结果复现了旧图中 S2/S4 的数百毫秒 VO/VI 尾部。当前统计没有把尾部压低；此前看起来很低的结果来自查看了轻载点或只看成功包，而旧 S2/S4 的大量低优先级包已最终失败或仍未完成。

## 4. 拐点细扫和 v2 选择

对 S2/S4 的 0.60、0.625、0.65、0.675 倍各运行 3 个新 seed。细扫发现 0.625 到 0.65 之间存在明显服务拐点：

| 组成 | 倍率 | 总交付 | VO交付 | VI交付 | BE交付 | BK交付 | VO/VI p95 (ms) |
|---|---:|---:|---:|---:|---:|---:|---:|
| S2 | 0.600 | 98.85% | 98.91% | 98.36% | 99.89% | 99.96% | 4.51 / 8.71 |
| S2 | **0.625** | **97.48%** | **97.79%** | **96.82%** | **96.39%** | **96.32%** | **6.09 / 11.93** |
| S2 | 0.650 | 93.23% | 96.41% | 94.62% | 57.61% | 66.73% | 8.06 / 14.97 |
| S4 | 0.600 | 98.43% | 99.61% | 99.52% | 93.18% | 98.91% | 2.88 / 5.71 |
| S4 | **0.625** | **94.84%** | **99.45%** | **99.20%** | **77.80%** | **80.35%** | **3.37 / 6.56** |
| S4 | 0.650 | 91.20% | 99.14% | 98.86% | 64.60% | 55.34% | 3.93 / 7.77 |

S2 v2 选 0.625，是因为实时和低优先级业务都受到可测竞争，但尚未进入 BE/BK 大面积饿死。S4 v2 同样选 0.625，用于保留实时业务的高完成率，同时形成明确的 BE/BK 服务权衡。旧 S2/S4 配置继续保存在 `configs/scenarios.yaml` 和历史结果中，新配置单独写入 `configs/scenarios_v2.yaml`。

## 5. v2 场景定义

| 场景 | 每 STA VO/VI/BE/BK (Mbit/s) | UL比例 | 类型与用途 |
|---|---|---:|---|
| S1 | 0.0751 / 0.3003 / 0.9761 / 0.1502 | 0.6 | 保留的平稳混合参考；Default EDCA 良好 |
| S2 | 0.3438 / 0.7813 / 0.2500 / 0.0500 | 0.5 | 实时业务临界竞争 |
| S3 | 0.0464 / 0.1857 / 1.8566 / 0.2321 | 0.7 | BE 主导且可服务 |
| S4 | 0.2813 / 0.6250 / 0.7500 / 0.1563 | 0.5 | 混合中高负载，考察优先级权衡 |
| S5 | 与 S2 v2 相同的时间平均值 | 0.5 | 每 STA 两状态动态突发，周期 5 s，低/高倍率 0.5/1.5 |

S5 对每个 STA 使用确定的相位偏移，避免全网同时切换造成不自然的同步尖峰。单个 STA 的负载仍在每 2.5 s 切换，网络总到达率则因相位错开较平滑。这使控制器面对“个别报告对象的负载变化”，而不是从仿真真值直接随机生成有利的 age。

3 个验证 seed 中，STA 1 的低状态平均到达率为 0.382 Mbit/s，高状态为 1.057 Mbit/s，高低比 2.77；设定比为 3.0，有限 2.5 s 窗口、边界处上一状态已抽取的到达间隔和泊松波动解释了差异。验证门槛为高状态至少达到低状态的 2 倍，已通过。

## 6. v2 Default EDCA 基线

采用 seeds 631/632/633、10 s 预热和 20 s 测量。下表的比例先按 seed 计算，再取均值；三 seed 的 95% t 区间在原始汇总表中保留。

| 场景 | 总交付 | 最终失败 | 未完成 | VO/VI按时完成下界 | VO/VI p95 (ms) | BE/BK交付 |
|---|---:|---:|---:|---:|---:|---:|
| S1 | 100.00% | 0 | 0 | 100.00% / 100.00% | 0.659 / 1.088 | 100.00% / 100.00% |
| S2 | 97.01% | 2.58% | 0.41% | 97.46% / 96.37% | 6.539 / 12.076 | 93.03% / 97.74% |
| S3 | 99.98% | 0 | 0.02% | 100.00% / 99.99% | 0.941 / 1.697 | 99.99% / 99.86% |
| S4 | 94.67% | 3.93% | 1.40% | 99.46% / 99.20% | 3.353 / 6.683 | 77.52% / 76.49% |
| S5 | 98.75% | 1.21% | 0.04% | 98.81% / 98.30% | 4.967 / 9.933 | 99.42% / 99.66% |

这里的“按时完成下界”是成功 ACK 且时延不超过 VO 20 ms、VI 50 ms 的包数除以测量窗口 at-risk 包数；截止时仍 pending 的包保守地不计按时。Reward-v2 实现前还会建立逐包 deadline ledger，严格排除尚未到期限的边界包，因此本表不能替代后续 Reward 统计。

结论不是所有新场景都要让控制器超过 baseline：S1 和 S3 明确保留 Default EDCA 已接近理想的事实；S2 提供仍可服务的实时竞争；S4 提供实时优先与 BE/BK 保障之间的优化空间；S5 用来检验 1 s 历史、异步报告和 age 是否对动态单站负载有实际价值。

## 7. 公开业务模型依据及当前边界

已保存 IEEE 802.11 TGax Evaluation Methodology 的官方文档和文本副本。该方法没有规定一个公认的固定 VO/VI/BE/BK 比例，而是分别定义业务生成器：VoIP 两状态活动模型、Weibull 视频帧与 Gamma 网络时延、FTP 文件/阅读间隔等。官方来源：

- [IEEE 802.11 TGax task group update](https://www.ieee802.org/11/Reports/tgax_update.htm)
- [11-14/0571r12 TGax Evaluation Methodology](https://mentor.ieee.org/802.11/dcn/14/11-14-0571-12-00ax-evaluation-methodology.docx)
- [11-14/0980r16 TGax Simulation Scenarios](https://mentor.ieee.org/802.11/dcn/14/11-14-0980-16-00ax-simulation-scenarios.docx)

本阶段的 S1–S4 仍是可复现的“固定包长/可变 VI 包长 + 泊松到达”控制压力场景，S5 是显式两状态到达率场景。它们没有被宣称为逐项复现 TGax 应用层。TGax 参数已独立记录在 `configs/traffic_models_tgax_reference.json`，包括 33/7 B VoIP 负载、20/160 ms 间隔、状态平均 1.25 s、2 Mbit/s 视频的 Weibull 参数以及 Gamma 网络时延。精确 VoIP/视频应用生成器将作为独立场景扩展，不会暗中替换本次标定，也不会修改已验证的 EDCA 核心。
